# 限流与重试

命令遇到 HTTP 429、需要控制批量导出的请求节奏，或判断由 CLI 还是 Agent 等待重试时读取。

## 诊断与控制请求节奏

从 CLI 的 HTTP 429 错误中读取限流原因和建议等待时间，需要响应头时查看脱敏的详细日志。响应头含义和服务端配额规则按 [API 文档检索](api-docs.md)核对，官方限流说明为 https://developer.pingcode.com/restapi/pingcode/limit。以目标部署实际返回的提示为准，不依赖 skill 中写死的配额。

单个 `pc` 进程无法协调其他共享企业配额的进程。多个任务同时遇到 429 时，优先串行执行并降低并发。

业务命令的 stdout 保持原生 JSON；HTTP 429 的限流原因和等待提示附在 stderr 错误中，不会改写成功响应。

## CLI 重试

全局参数示例：

```sh
pc --retries 3 --max-retry-wait 60 pjm workitem list --project-id <id>
pc --retries 0 ...   # 关闭自动重试
```

通过 `pc --help` 查看已安装版本的默认值。只有**安全读请求**自动重试，包括 GET/list、结构化 `search`（使用 POST，但属于读操作），以及 CLI 明确按读处理的 Nexus 操作。不要仅凭操作名判断重试安全性，也不要套用到任意 POST 或自定义路由。

写操作、语义未知的 Exposer 非 GET 路由、multipart 上传及其他非幂等操作**不会自动重放**。分页只重试**当前页**。批量响应应保留成功项，仅重试确认失败的条目，不得整批重新提交。

CLI 的等待受 `--max-retry-wait` 限制。服务端要求的等待超过剩余预算时，CLI 返回限流错误；不要立即重试或截短等待来绕过该结果。

## 避免双重退避

安全读优先使用 CLI 的有界重试。`--retries` 大于 0 时，不要再对同一请求叠加 Agent 重试循环。写入结果不确定时，先检查资源是否已经存在，再决定是否手动重试。鉴权请求遇到 429 时也应等待建议时长，不要用紧密循环反复提交凭据。
